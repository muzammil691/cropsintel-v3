## Remediation attempt 3 (2026-05-07, after Verifier `judgment-synthesis-judgment-text-fail` rejection)

Attempt 2 (commit `00ab384`, ADR shipped with `38ec656`) was rejected by the Verifier with a synthesised gap `judgment-synthesis-judgment-text-fail` (severity `fail`). The condensed judge-notes excerpt embedded in the gap's `actual` field shows both judges' free-text concluded **pass**:

> *"ADR explaining root-cause is provided at the required path and states that no code fix is needed, meeting the 3 acceptance points; follow-up spec is referenced as already present, so criteria for gap is met. / The agent has correctly diagnosed a complex, recursive issue where the Verifier was failing on an investigation task about Verifier failures. The submitted ADR is exceptionally thorough, providing a clear root cause analysis…"*

The judges therefore emitted no gaps. The synthesised gap was generated downstream by `verifier/src/lib/gaps-builder.ts:ensureFailGap` because `verifier/src/lib/verdict-resolver.ts:58` resolved verdict→fail purely from `parseJudgmentText` keyword regex.

### Why the council parser regex flagged judges' own pass-text

`verifier/src/lib/council-parser.ts:15` defines:

```
FAIL_KEYWORDS = /\b(fail(?:s|ed|ing|ure)?|missing|absent|deficien\w*)\b/gi
```

The judges' pass-writeup of an ADR whose **subject** is a Verifier failure cluster necessarily uses words like *"Verifier failures"*, *"Verifier was failing"*, *"investigation task about Verifier failures"*, *"complex, recursive issue"* (with `fail` matching `failures`/`failing`). None of these hits sit within the 40-char negation window in `verifier/src/lib/council-parser.ts:17` (`NEGATOR_BEFORE`), so `findHits` returns ≥1 unnegated fail hit and `parseJudgmentText` returns `verdict: 'fail'`.

`verifier/src/lib/verdict-resolver.ts:58` then short-circuits to `verdict: 'fail'` regardless of either judge's actual `passed: true` boolean or empty-`gaps[]` payload, and `gaps-builder.ts:ensureFailGap` synthesises the `judgment-synthesis-judgment-text-fail` row that requeued this cluster a third time.

This is a **subject-matter / verdict ambiguity** in the council parser. The regex cannot distinguish:

1. *"This work failed"* — a verdict (fail keyword should bind),
2. *"This work investigates a Verifier failure"* — subject matter (fail keyword is a noun about what is being analysed, not a verdict on the analysis itself).

For investigation/ADR specs whose **goal is to diagnose a failure**, every honest pass-writeup will contain `failure`/`failing`/`missing`. The parser will then over-trigger on every such writeup forever. Bug B3-class.
