## The new entry: when an investigation task gets caught in its own failure pattern

`phase-1-CLUSTER-investigation-1778152873297` was the autonomous run that produced commit `153c17a` at 11:39:43 UTC — three minutes before the conductor flagged this cluster at ~11:40:00 UTC. That commit was **not** a 0-file commit; `git show --stat 153c17a` confirms three files / 174 insertions:

| file | lines |
|---|---|
| `docs/atlas-decisions/ADR-2026-05-07-verifier-cluster-1778152873297.md` | +76 (newly created) |
| `.agent/tasks/in-progress/phase-1-CLUSTER-investigation-1778152873297.md` | +4 (the agent appended a `## Files` section pointing at the ADR) |
| `.agent/tasks/logs/phase-1-CLUSTER-investigation-1778152873297-*.log` | +94 |

The agent-loop log for that run ends with `Build is green. The investigation is complete.` and `[agent-loop] claude exit code: 0`. The build passed locally. So the failure had to be Verifier-side, *after* the commit landed.

The spec file at `.agent/tasks/in-progress/phase-1-CLUSTER-investigation-1778152873297.md` (current HEAD) has exactly one entry under `## Files`: the ADR path, which **was** created by the commit. So this is *not* the canonical Bug B2 case (deliverables shipped in a prior commit) — it is a closely related but distinct false-negative on investigation-style specs.

The cluster trigger row records "no detail" for the verdict, so the gap text is not preserved here. From the recurring pattern, the most likely cause is that the Verifier's AI judges read the spec's `## Goal` and `## Acceptance criteria` sections — which talk about diagnosing all three constituent task IDs and producing root-cause findings for each — and judge the ADR as not satisfying the goal because it (correctly) defers the underlying B1/B2 fixes to follow-up tasks (per acceptance criterion 2). In other words, the judges may be applying a "did the deliverable fix the problem" lens to a task whose explicit deliverable is "diagnose, do not fix". This is a third manifestation alongside B1 and B2; we'll call it **B3 — judges fail-fast on investigation/ADR-only specs whose acceptance criteria explicitly forbid shipping a fix**. It is plausible but not confirmed without the Verifier output.

## Why the conductor fired again

The conductor queued this cluster (commit `90f4338`, ~11:42 UTC) two minutes after the prior investigation closed (`153c17a`, 11:39:43 UTC). The prior ADR's recommended dedupe upgrade — *"match any queued cluster in trailing 30 min" + "match closed ADR"* — would have caught this fire (2-of-3 task IDs are cited under the just-closed `1778152873297` ADR), but that recommendation is still on the conductor track and has not shipped. So the conductor cannot yet dedupe.

A separate gap: the mark-shipped tactical follow-up created by `ADR-2026-05-07-verifier-cluster-1778153395522.md` is sitting at `.agent/tasks/queued/phase-1.6e-adela-scheduler-health-server-fix-4-of-5-mark-shipped.md` (committed in `56bd7dd` at 11:44 UTC) but has not been picked up by the agent-loop yet. As soon as it runs, the rem2/rem3 specs will move to `done/` and the rem-chain half of this cluster will stop firing. That alone will eliminate two of three IDs in the next cluster window.

## Root cause

**Same as `ADR-2026-05-07-verifier-cluster-1778152873297.md`** for the rem-chain entries (B1 + B2). For the new third entry (`phase-1-CLUSTER-investigation-1778152873297`), the most plausible explanation is **B3** — judges over-applying a "did this commit fix the problem" lens to an investigation-only spec — but this is hypothesis-level, not confirmed, because the Verifier's gap text is not preserved in the cluster trigger record.

## Decision

**Close cluster `1778154179464` as a duplicate of `1778152873297`** with no new code change. The follow-ups documented in the prior two ADRs remain the canonical fix path. No new tactical task is queued by this ADR — the mark-shipped task already exists in the queue and is sufficient to clear two of three IDs in this window.

The one piece of new information surfaced by this cluster is candidate **Bug B3** (judges fail-fasting on investigation/ADR-only specs). It is added below as a follow-up, with the caveat that confirmation requires the actual Verifier gap text from the `phase-1-CLUSTER-investigation-1778152873297` audit — which the conductor's cluster-trigger record does not carry today. **Improving the conductor to forward the Verifier gap text into the cluster spec would have made this ADR conclusive** and is itself a small follow-up.
