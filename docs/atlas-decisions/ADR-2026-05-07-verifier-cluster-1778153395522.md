# ADR — Verifier cluster `1778153395522` is a duplicate trigger of `1778152873297`; close, no new action

## Context

Atlas conductor flagged a 3-failure Verifier cluster in a 30-minute window:

| time (UTC)              | task                                                            |
|-------------------------|-----------------------------------------------------------------|
| 2026-05-07 11:08:09     | `phase-1.6e-adela-scheduler-health-server-fix-4-of-5-rem`       |
| 2026-05-07 11:13:14     | `phase-1.6e-adela-scheduler-health-server-fix-4-of-5-rem2`     |
| 2026-05-07 11:27:02     | `phase-1.6e-adela-scheduler-health-server-fix-4-of-5-rem3`     |

This cluster's window has slid forward by exactly one entry from the prior cluster `1778152873297`: the original `phase-1.6e-adela-scheduler-health-server-fix-4-of-5` has aged out and been replaced by `-rem3`. The remaining two task IDs (`-rem`, `-rem2`) are identical. **All three task IDs are already cited under** `ADR-2026-05-07-verifier-cluster-1778152873297.md`.

The conductor queued this cluster (commit `2d4780a`, ~11:30 UTC) *while* the prior cluster's investigation was still mid-flight (the prior ADR did not land until `153c17a` at 11:39 UTC). So the conductor did not see the prior ADR at queue time and could not dedupe.

## Root cause

Same as `ADR-2026-05-07-verifier-cluster-1778152873297.md`: **Bug B (B1 + B2) on the `phase-1.6e` rem-chain.** No new failure mode in this cluster.

Re-stated briefly: the rem-chain spec asks for files that already exist on disk from a prior dev-authored commit (`1dd90dd`, `1b0e75d`). The Builder sees the files exist, commits 0 functional files (B1). The Verifier's AI judges read the empty diff and answer "missing implementation" even though `loadShippedCodeContext` surfaces the existing files (B2). Atlas auto-requeues, the loop runs forever.

## Decision

**Close cluster `1778153395522` as a duplicate of `1778152873297`** with no further investigation work. The follow-ups documented in the prior ADR remain the canonical fix path; nothing new to add.

The prior ADR's recommended `mark-shipped` follow-up task spec was *named* but not *created* by that investigation. To break the requeue loop tactically before B1/B2 are properly fixed, this ADR ships that follow-up spec as a queued task — that is the only side effect of this investigation.

## Follow-ups

1. **`phase-1.6e-adela-scheduler-health-server-fix-4-of-5-mark-shipped`** — **created by this ADR** at `.agent/tasks/queued/phase-1.6e-adela-scheduler-health-server-fix-4-of-5-mark-shipped.md`. A two-line tactical task: move the rem2/rem3 spec files from `in-progress/` to `done/`, so the auto-requeue loop stops re-firing this lineage. The implementation already exists in `1dd90dd` + `1b0e75d`.
2. **Bug B1** (Builder allowed to commit 0 functional files) — open, agent-loop track. Unchanged from prior ADR.
3. **Bug B2** (judges treat empty diff as missing implementation) — open, verifier track. Unchanged from prior ADR.
4. **Conductor cluster dedupe** — open, conductor track. This cluster is a clear example of the gap: the conductor queued `1778153395522` ~9 minutes after `1778152873297` for an overlapping set of task IDs (2 of 3 identical). The dedupe rule should match clusters whose task-ID set has ≥50% overlap with any cluster queued in the prior 30 minutes, not just clusters cited under a *closed* ADR (the prior ADR hadn't closed yet at queue time). Recommendation upgraded from "match closed ADR" to "match any queued cluster in trailing 30 min" + "match closed ADR".
